# CRM 商机与客户维护

仅使用 `ifeishu_base_query` / `ifeishu_base_write`，拿到链接先 inspect，首次批量操作先 conventions。读取本机 `~/.cc-switch/local-context/ifeishu-resources.json` 的 crm 部分可定位已知资源；其中 ID 属于本地业务资料，不随技能仓库同步。文件缺失时使用用户提供的真实链接，不猜 token。历史表数量、字段数和枚举不作为当前真相。

## 定位和写入

1. 用真实 app 确认表，用 table_id + list_fields=True 读取当次字段定义。分页读取记录，依据名称/上下文确认 record_id；展示主字段不是稳定唯一 ID。名称重名或匹配不明时先消歧。
2. 先看现值，只发送本次要改的字段。空缺信息不臆造；现有值不能因为用户没提到就清空。Lookup、公式及系统生成字段只读。
3. 新增前检索重复。新客户先创建并取得真实 record_id，再写商机的客户关联；避免两边重复写双向关系。
4. `ifeishu_base_write` 使用批量端点，每批最多 500 条，工具公共参数中的 records 是对象数组。create 用 `fields`；update 用 `record_id` + `fields`；delete 用 `record_id`，删除需用户已确认具体目标。不要把服务内部 batch_delete 的字符串数组直接当公共 MCP 参数。
5. 检查实际逐项状态与返回结构，不能只看顶层成功。部分成功不回滚；不确定结果先读现状，只补做确认失败项，避免重复商机或日志。完成后回读目标字段。

## 业务规则

| 字段/场景 | 规则 |
| --- | --- |
| 商机金额（万美元） | 单位是万美元，150 表示 150 万美元；用户金额的币种/单位不明时先澄清 |
| 待办截止时间 | DateTime 按当前字段结构用 epoch 毫秒；代码显式采用用户时区计算，不依赖系统默认时区 |
| 项目日志 | 先读完整旧值，再按 `M月D日 事件` 追加新行；保留旧行和顺序。写入是替换字段值，不是服务器原子追加，重试前检查已写内容 |
| 客户关联 | 从当前客户表取得 record_id 数组；不猜关联值 |
| 销售/国家地区 | 商机侧历史为 Lookup，按当前结构确认；需要修改时通常改关联客户的源字段，不写 Lookup |
| 咨询/方案 | 咨询负责售前需求，方案负责技术架构；销售在客户侧统一维护。按当前字段单/多选约束构造人员对象 |
| 人员 ID | open_id 有应用命名空间，从当前 Base 既有人员字段或已确认映射取得；不能拿 IM/Gateway 的 ID 直接写入。1254066 时核对来源，不试猜 ID |
| 枚举 | 读取当次选项；新增业务枚举需用户确认，不沿用历史固定国家/行业数量 |

MCP 不可用时检查当前应用连接和自检，使用 `ifeishu-mcp-ops` 排障；不回退 shell CLI、未经授权的新建本地台账或猜测平台状态。工具当前不暴露的表结构维护明确交给 Web UI 或单独服务维护任务。
